# 2026-11-01 开发与测试记录

## 一、工程现状与可测试范围

工程为 Python 算法后端，核心链路为 YOLO Pose 人员姿态检测、ByteTrack 跟踪、场景坐标投影、区域人数判断和班组合格工时累计。今天新增本地前端测试工作台。

目前无法连接现场实时监控，因此以历史视频离线分析作为主要测试路径。

| 模块 | 当前可测试内容 | 限制 |
| --- | --- | --- |
| 相机管理 | RTSP/RTMP 地址登记、参数校验 | 尚无完整相机列表、编辑、删除管理功能；现场连通性待验证 |
| 历史分析 | 创建记录、上传 MP4 和专属场景图、代表帧、标定划区、保存配置、启动/停止/重试、进度查询 | 完整视频识别与工效准确性仍需人工验收 |
| 实时分析 | 提交配置、创建/查询/停止任务 | 实际分析需要可访问的视频流；现场延迟、断流重连及长期稳定性待验证 |
| 结果查询 | 最新人员结果、区域工效、时间区间汇总、保存任务查询、逐帧分页查询 | 尚无可视化历史轨迹及骨架回放 |
| 场景管理 | PNG/JPEG 上传、预览、标定和区域校验 | 尚无完整列表、编辑、删除管理功能 |

“工作”目前主要按人员是否处于工作区域判定，不等于识别了具体施工动作。有效计工人数可能包含区内丢失保留人数和离开宽限人数，因此可能大于当前可见人数。确认离开后采用20分钟宽限，原有离开防抖参数不应改成1200。

5. 设置计划人数、要求工时、人员置信度、进出防抖。
6. 保存配置、启动任务、查询结果、自动刷新、停止任务。
7. 查询工效汇总、下载当前查询 JSON。

其他页面提供相机登记、实时配置 JSON 提交、实时任务启动、实时场景图上传预览。实时配置的初始坐标仅为结构示例，必须替换为真实标定数据。

### 2. 持久化方案调整

今天先实现 SQLite，随后根据测试需求改为按任务文件夹保存 JSON。**最终默认方案是 JSON 文件，旧 SQLite 文件保留，但不自动迁移或继续写入。**

新增 `src/work_efficiency_perception/persistence.py`，默认 `main:app` 使用 JSON 仓储；直接调用 `create_app()` 仍默认使用内存仓储供独立测试。

默认保存结构：

```text
data/results/
  resources.json
  tasks/<taskId>/
    task_configuration.json
    snapshot.json
    efficiency_overall.json
    persons/
      frame_000000000000.json
    efficiency_30s/
      at_000000000030.json
      at_000000000060.json
```

| 文件 | 内容 |
| --- | --- |
| resources.json | 资源恢复索引，包括场景、配置、相机、视频元信息、历史分析及任务记录 |
| task_configuration.json | 任务状态、完整配置、计算得到的3×3转换矩阵 homography、视频信息及场景图片 |
| snapshot.json | 最新分析结果、进度、帧计数及时间区间，供重启恢复查询 |
| efficiency_overall.json | 截至当前的整体工效累计、区域人数及达标/不足时间区间；完成时保留最终结果 |
| persons/frame_*.json | 每个实际推理帧的人员框、骨架、人员ID、场景投影、区域状态、轨迹增量及区域统计 |
| efficiency_30s/at_*.json | 每30秒节点的当前工效情况 |

矩阵约定：视频像素坐标经 homography 投影为场景归一化坐标，需进行齐次除法；完整配置保留标定点及标定误差。场景图片以 Base64 放在 JSON 内。原始 MP4 仍保存到 `data/videos/<analysisId>/`，不重复保存每帧原始画面，也不生成带骨架视频。

30秒快照按输入帧时间戳触发。历史视频按视频时间的30、60、90秒等节点保存，不按程序运行耗时保存。取节点之后首个实际推理帧，并记录节点时间 `scheduledTimestampSec` 与实际 `timestampSec`。若跨过多个节点，不插值、不伪造中间观察，只保存实际到达时段的快照。末尾不足30秒的部分仍进入整体结果。

历史视频默认约每200ms推理一次，人员归档保存的是实际推理帧。`poseSamplingMs` 暂不用于二次抽样。`persistPoseAndTrajectory=false` 时不落盘人员明细，但仍保存区域统计；当前进程中的最新人员结果仍可查询。

服务重启后会恢复已保存任务和结果；未完成任务标记为 FAILED，历史任务可从头重试，不恢复跟踪器和计工状态。已保存的阶段结果保留。新重试会生成独立任务记录。

可使用环境变量 `WORK_EFFICIENCY_RESULTS_DIRECTORY` 指定保存目录。当前仅支持单个服务进程使用同一目录，不要同时启动多个进程写入同一份结果目录。

新增接口：

- `GET /api/work-efficiency/v1/tasks`：任务列表。
- `GET /api/work-efficiency/v1/tasks/{taskId}/frames?afterSeq=-1&limit=100`：按帧号分页读取，使用返回的 nextAfterSeq 继续，limit 最大1000。

### 3. Windows 文件占用修复

实测中任务在视频约13秒时失败：已解码391帧、已推理66帧，替换 `efficiency_overall.json` 时出现 WinError 5 拒绝访问。可能与百度同步目录中的短暂文件占用有关，尚未确定具体占用进程。

修复内容：

- 使用唯一名称的同目录临时文件，避免临时文件名冲突。
- 写入后执行 flush/fsync，再原子替换目标文件。
- Windows权限或共享占用类错误进行有限重试，最多11次替换尝试。
- 持续失败时保留旧的完整目标文件，清理临时文件；不静默忽略保存失败。

单文件更新是原子的，但多个 JSON 文件不是一个数据库事务，异常断电时最后一帧归档与汇总可能不同步。当前无自动清理策略，长期测试需关注磁盘空间和文件数量。

## 三、今天遇到的问题及操作说明

### 页面404

根路径 `/` 没有页面，需打开完整地址 `http://127.0.0.1:8003/test-ui/`。`favicon.ico` 404只是缺少图标，不影响测试。8000端口被占用后改用8003。

### historical video is unavailable

选择本地文件并不等于上传成功。需要点击“上传视频”，等待成功后再获取代表帧。记录中 `video: null`、状态 EMPTY 表示尚未完成视频上传。

### historical analysis is not ready

日志显示缺少 CONFIGURATION。视频与场景上传完成后，还需要配对标定点、完成工作区域并点击“保存历史配置”，再启动任务。“区域至少需要三个点”表示绘制区域尚未完成。

### RUNNING但帧数为0

表示工作器已启动，但还没有第一帧结果，可能正在加载模型。开启自动刷新观察推理帧数是否增长；若长时间不增长，检查PowerShell模型加载或视频读取日志。出现人员结果后才能确认已产生推理输出。

### FAILED与保存拒绝访问

今天的截图表明任务实际运行过，但因保存失败中止，并非模型没有检测到人。更新代码并重启服务后，可读取原历史分析记录再启动，从头重试，无需重新上传素材或标定。

## 六、让同事访问

### 同一局域网

运行上述 `--host 0.0.0.0` 命令后，使用 `ipconfig` 查当前网卡IPv4。同事访问：

```text
http://你的局域网IP:8003/test-ui/
```

同事不能使用127.0.0.1，那指向他们自己的电脑。必要时在可信专用网络中允许Python或TCP8003入站，并确认网络没有设备隔离。不能把0.0.0.0作为同事浏览器的目标地址。

### 不同局域网（当前实际情况）

普通192.168.x.x地址无法跨公网直接访问。讨论了两种方案：

1. 虚拟局域网：例如Tailscale、ZeroTier，双方安装并加入同一虚拟网络，然后使用你的虚拟IP和8003端口访问。适合固定同事反复测试。
2. 内网穿透：生成公网HTTPS入口，适合临时浏览器访问，但应先配置访问认证。

**当前只讨论方案，尚未安装、配置或验证跨网络访问。** 下一步先确定同事是否方便安装组网软件，再执行配置。当前工作台有共享任务与上传能力，不宜无认证公开。
