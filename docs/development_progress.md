## 2026-11-03 历史视频流程与物料对齐

当前标准调用为 `POST /videos → POST /scenes（videoId）→ POST /configurations（videoId）→ POST /tasks（VIDEO_FILE）`，分别取得 videoId、sceneId、configurationId、taskId。通过 `PATCH /tasks/{taskId}` 停止；全局单历史任务与实时相机任务分开调度；实时按相机互斥，历史停止中仍占名额，终态后可以新建任务从头分析。

详见 [当前历史视频接口规范](history_video_api.md) 和 [本次修改记录](2026-11-03历史视频流程对齐记录.md)。旧 historical-analyses 路由保留兼容，0825/0902 Word 中的旧历史流程不作为新对接依据。默认入口已经使用本地 JSON 持久化。

## 2026-10-31 班组连续计工更新

以下规则替代本文早期的“短时丢轨容忍”和“仅 INSIDE 计入人数”描述：

- 区内检测丢失、未观察到出界时，无限保留班组计工人数。
- 出界防抖期间继续计工，确认出界后宽限 20 分钟；到期扣减，不回扣宽限期已累计工时。
- 同区域成员补入优先抵消临时离开人数，不要求长期人员身份一致；新 ID 区内重现可接替当前不可见的保留名额。
- 班组有效计工人数和当前可见人数分开：`actualWorkingCount` 包含保留/宽限人数，`persons` 仍只输出当前检测人员。
- 前端请求及响应字段结构不变；`exitDetectionDurationSec` 仍用于防抖，20 分钟采用后端默认策略。
- 宽限期到期时间用于切分工时与合规区间；保留原有长帧间隔计时保护。
- 此策略无法可靠区分遮挡后新 ID 重现与未拍到进入的新成员，现场须验证出入口可见性和人数误差。

详细规则参见 README 的“班组连续计工规则”。下文测试数字及早期验证结果保留为当时记录。

## 1. 总体进度

当前后端整体完成度约为 **80%**。

已经打通以下主要链路：

```text
创建实时配置或独立历史分析记录
→ 绑定实时相机，或上传专属视频和场景图
→ 保存对应类型的标定和工作区域配置
→ 创建分析任务
→ 人员姿态检测和跟踪
→ 俯视图投影及区域判断
→ 区域人数和工效累计
→ HTTP 查询或 WebSocket 实时推送
```

当前数据主要保存在进程内存中，服务重启后会丢失。MySQL、历史回放、正式鉴权和现场海康相机验证计划后续实施。

## 2. 已完成功能

### 2.1 场景与工效配置

- 上传 PNG/JPEG 场景俯视图；
- 校验图片格式、20 MB 大小限制和图像尺寸；
- 接收前端提交的相机点、场景点和工作区域；
- 校验至少 4 组标定特征点；
- 计算相机画面到归一化场景坐标的单应矩阵；
- 计算平均和最大重投影误差；
- 校验工作区域坐标、重复 ID、自交和零面积；
- 校验计划人数、要求时长及算法参数；
- 生成不可变的配置、标定和区域版本；
- 实时配置和历史配置分开保存并禁止交叉使用；
- 历史配置与单个 `analysisId`、视频和场景图绑定。

### 2.2 人员检测与跟踪

- 接入 Ultralytics YOLO Pose；
- 接入 ByteTrack，并持续保持视频内 `trackId`；
- 输出人员置信度、检测框和 COCO 17 个姿态关键点；
- 每个任务应用自身配置的 `personConfidence`；
- 优先使用双脚踝中点作为地面锚点；
- 脚踝置信度不足时退化为检测框底边中心；
- 支持 GPU/CPU、推理尺寸和跟踪器配置；
- 默认使用 `model/yolo11m-pose.pt`，也可通过环境变量覆盖。

### 2.3 视频与实时流

- 历史 MP4 上传和登记；
- 历史视频不依赖 `cameraId`、实时相机状态或实时配置；
- 每个历史分析记录绑定一个视频、一张专属场景图和一套历史配置；
- 自动读取分辨率、FPS、总帧数和视频时长；
- 按视频时间戳处理历史视频，不按程序耗时累计工效；
- 历史视频默认每 200 ms 抽取一帧执行模型推理，并保证分析首帧和末帧；
- 区分已解码原始帧数和实际模型分析帧数；
- 正常读完后将进度归一为 100%，明显提前解码中断时任务失败；
- 支持 RTSP/RTMP 实时相机地址登记；
- 历史视频和实时流使用统一 `FrameSource` 分析流程；
- 实时流读取与算法推理解耦；
- 实时流只保留最新帧，避免延迟持续堆积；
- 支持首次连接超时、断流重连和协作停止。

### 2.4 区域判断与工效算法

- 将人员地面锚点投影到场景俯视图；
- 多边形边界包含的区域判断；
- `OUTSIDE/ENTERING/INSIDE/LEAVING/UNKNOWN` 状态机；
- 进入和离开持续时间防抖；
- 短时丢轨容忍；
- 人员处于 `INSIDE` 时标记为 `WORKING`；
- `INSIDE` 人员计入 `actualWorkingCount`；
- 人数达到 `expectedWorkerCount` 时累计班组合格工时；
- 计算 `headcountCompliant` 和 `efficiencyStatus`；
- 保存人数符合/不足时间区间；
- 修复 `qualifiedTeamWorkDurationSec` 在进入确认帧提前累计的问题；
- 限制过大帧间隔，避免断流导致工时虚增。

### 2.5 任务管理

- 使用独立入口创建实时相机任务或历史视频任务；
- 历史任务启动后锁定视频、场景图和配置；
- 历史任务失败或停止后允许从头重试，完成后禁止重复执行；
- 查询任务状态；
- 幂等停止任务；
- 后台线程执行分析；
- 支持以下任务状态：
  - `CREATED`
  - `STARTING`
  - `RUNNING`
  - `STOPPING`
  - `STOPPED`
  - `COMPLETED`
  - `FAILED`
- 支持任务取消、线程池关闭和排队任务清理；
- 记录模型执行异常和失败原因；
- 修复启动与停止同时发生时可能卡在 `STOPPING` 的竞争问题。

### 2.7 WebSocket 实时推送

已实现规范地址：

```text
/ws/work-efficiency/v1/tasks/{taskId}
```

支持：

- `FRAME_RESULT` 实时分析消息；
- `ERROR` 错误消息；
- 帧序号、尺寸和 ISO 8601 `capturedAt`；
- 人员置信度、检测框、姿态关键点和地面锚点；
- 场景坐标、区域归属、工作状态和轨迹增量；
- 区域实际人数、计划人数、合格状态和累计工时；
- Bearer Header 或 `access_token`；
- 慢客户端只保留最新结果，不阻塞模型推理；
- 任务进入终态后结束推送；
- WebSocket 消息不包含历史视频处理进度。

### 2.8 响应与错误处理

- 统一 HTTP 响应字段：`requestId/success/code/message/data/timestamp`；
- 已覆盖主要错误码：
  - `WE0101` 参数错误；
  - `WE0102` 标定无效；
  - `WE0103` 区域无效；
  - `WE0104` 工效参数无效；

## 8. 2026-09-02 历史视频独立分析流程

### 8.1 业务结论

历史视频分析与实时视频分析在业务入口、资源归属和配置存储上隔离。历史视频不再依赖 `cameraId`、实时相机在线状态或实时配置。两类任务继续复用视频读取、人员检测、跟踪、空间投影、工效引擎、任务状态和结果结构。

第一版以 `analysisId` 为流程根对象，一个历史分析记录对应一个视频、一张不复用的场景图和一套历史配置。

### 8.2 历史视频分析流程

```text
创建 historical analysis，取得 analysisId
→ 上传专属 MP4
→ 上传专属场景图
→ 选择代表帧并提交视频点/场景点
→ 划定区域并保存历史配置
→ 创建 HISTORICAL_VIDEO 任务并锁定输入
→ 后台按视频时间戳执行人员姿态、区域人数和工效分析
```

配置在任务启动前允许覆盖修改；替换视频或场景图会清空已有历史配置。任务启动后输入和配置锁定。失败或停止的任务可以基于同一输入从头重试，同一时间只允许一个非终态任务；完成后第一版禁止重复执行。

### 8.3 前端联调注意事项

- 视频和场景图分开上传，避免大文件失败后整体重传；
- 视频必须先于场景图上传；
- 视频标定点使用原始视频像素坐标，场景点使用原始场景图像素坐标；
- 工作区域继续使用场景图归一化坐标；
- 历史配置不得传给实时任务，实时配置也不进入历史配置流程；
- `LOCKED` 状态修改输入或配置时，引导用户新建历史分析记录。
